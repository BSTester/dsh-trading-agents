## 一、接入方式

以下信息全部来自快速开始页实测文案。

### API Host

| 通道 | 地址 |
|---|---|
| HTTP API（REST） | `https://webapi.futunn.com` |
| WebSocket 行情推送 | `wss://webapi-quote.futunn.com/ws` |
| WebSocket 交易推送 | `wss://webapi-trade.futunn.com/ws` |

页面原文：「本套接口为标准 REST / HTTP，任意语言用 HTTP 客户端即可调用，无需安装专用 SDK。」

### 认证方式（两种，二选一）

| 方式 | 官方推荐度 | 请求头 | 适用场景（页面原文口径） |
|---|---|---|---|
| OAuth 2.1 + PKCE | 推荐 | `Authorization: Bearer {access_token}` | 第三方应用、用户授权、代表用户访问账户/交易资源 |
| 传统 API Key（非对称签名） | 兼容 | `X-Api-Key` + `Authorization: {signature_base64}`（**无 Bearer 前缀**）+ `X-Timestamp` + `X-Nonce` | 「服务端自有系统、后端定时任务、内部工具」 |

对平台 daemon 场景，两种都能落地：

- **API Key 方式更贴合 daemon**：在 [open.futunn.com/dashboard](https://open.futunn.com/dashboard) 用户中心创建 AppKey 并上传公钥，支持 `Ed25519` 与 `RSA-SHA256`（PKCS#1 v1.5 + SHA256）。每次请求用私钥对签名原文（`timestamp_ms`、HTTP 方法、request_path、query_string、body 的 SHA256 十六进制摘要，共 5 字段，以 `\n` 连接，空字段保留位置）签名后 Base64。`X-Nonce` 为 1–64 位防重放随机串。
- **OAuth 2.1 + PKCE**：动态注册客户端（`POST /oauth2/register`）→ 浏览器授权（授权码 5 分钟有效、一次性）→ `POST /oauth2/token` 换 token。`expires_in` 实测样例为 **7200 秒**，`refresh_token` 刷新且**不轮换**。scope 样例含 `quote:read quote:write trade:read trade:write accid:*`。页面安全要求：**token 不要存环境变量**（应加密文件/密钥链），私钥不得入库。

### 是否需要 OpenD

- 快速开始页**全文未提及 OpenD**：REST 直连云端 Host，两条 WS 也是云端 `wss://` 域名，据此判断**不需要 OpenD 本地网关**。这与我们现用的富途远程 MCP（拉取式）同一云服务形态，而与旧版 `futu-api`（必须先起 OpenD 进程）不同。
- 但页面没有一句显式的「无需 OpenD / 与 OpenD 体系的关系」说明，严谨起见列入待确认。

**待确认问题清单**（页面信息不足处）：

1. 本 REST API 与旧版 futu-api/OpenD 体系是否并存、数据与权限口径是否一致？
2. 历史 K 线 `autype` 复权参数的具体枚举值（页面确认存在、默认 `1`；三种复权口径对应值在命名词典页，未抓取）。
3. WebSocket 交易推送的事件类型清单、订阅粒度与配额（仅确认了入口域名与「概览/鉴权/订阅/保活」文档结构，子页未抓取）。
4. OAuth refresh token 的调用频率是否单独限频；daemon 长期运行的续期实践。
5. 全市场标的清单接口（`stock-basicinfo`）的分页上限与一次全量拉取的请求数。
6. 行情推送 K 线订阅是否计入账号级订阅总额度（官方页自述「应以生产环境实际返回为准」，未定论）。

## 二、限频与配额

接口限频总览页只给**原则**（批量、缓存静态数据、错峰、429 + `Retry-After` 指数退避），唯一给出的具体数字是：行情快照批量 `code_list` **最多 400 个/请求**。历史 K 线页给出的是**每请求条数**而非频率：`num` **默认 370、最大 370**，支持 `next_time` 向更早翻页。

**推送订阅数上限**：行情推送配额页明确「**不提供固定数值限制**」——配额按连接、订阅（账号级总额度 `uid_total_quota`，订阅项 = 标的 + 数据类型，K 线再按周期/复权细分）、行情权限档（LV1/LV2/LV3、港股经纪队列）、控制消息频率四个维度动态校验，超限返回 `code = 4`（"sub quota exceeded"）。因此**订阅上限必须以我们账号实测为准**。

### 「全市场 ~1.5 万标的回填」耗时估算

历史 K 线是**单标的接口**（symbol 在路径里），没有批量参数；快照类才能 400 合 1。所以请求数下限 = 标的数 × 翻页数：

| 回填口径 | 每标的请求数 | 总请求数（~1.5 万标的） |
|---|---|---|
| 近 1.5 个交易年日线（≤370 根，1 页拿满） | 1 | ~1.5 万 |
| 2023 年起日线（约 900 根，`TOOL-LIMITS.md` 实测口径） | ⌈900/370⌉ = 3 | ~4.5 万 |

耗时 = 总请求数 ÷ 实测每分钟可用请求数。**官方未公布历史 K 线的每分钟/每日配额**，下表速率全部是**假设值（非官方数字，待实测回填）**：

| 假设速率 | 1.5 万请求（1 页/标的） | 4.5 万请求（3 页/标的） |
|---|---|---|
| 30 次/分钟 | ≈ 8.3 小时 | ≈ 25 小时 |
| 60 次/分钟 | ≈ 4.2 小时 | ≈ 12.5 小时 |
| 120 次/分钟 | ≈ 2.1 小时 | ≈ 6.3 小时 |

解读：daemon 化后即使按保守的 30 次/分钟假设，隔夜也能完成全市场日线回填；这在 MCP 对话通道里不可行（会话时长与上下文都不允许），是走 OpenAPI 的结构性收益。**第一笔投入应是 10 标的 × 连续 1 分钟的限频实测**，用实测值替换上表。

## 三、对平台三个增量的落地评估

接入点统一为 `trading_datasource` 新源 **`futu_openapi`**（`plugins/datasource/python/trading_datasource/futu_openapi.py`，与现有 `futu_mcp.py` 并列；**WP13 任务 0 起拆为同名包 `futu_openapi/`**，对外导入路径不变——护栏见 `tests/test_wp12_openapi_package.py` 的历史命名空间与「禁止内联路径字面量」断言），行情路由仍收敛在 `market.load_bars` 一处，符号转换/复权口径/失败上报沿用「唯一实现」原则。

### 1. K1 原始价回填

- **增量点**：历史 K 线接口原生携带 `autype` 复权参数（默认 `1`），同一接口可切换复权口径取数并配合 `next_time` 翻页回填；日 K 字段直接含 `last_close`/`pe_ratio`/`turnover_rate`，落库原始价不需要二次推导。注意：该接口每请求上限 370 根，与我们 MCP 工具实测一致，「原生上限更高」的说法在页面**未获证实**（见待确认 #2、#10）；真正的增量是**复权口径参数化 + REST 直连可批量翻页**。
- **前置条件**：AppKey 凭据与签名模块；限频实测数字；`autype` 枚举确认。
- **工作量**：**M**（签名/认证 + 限频退避 + 翻页回填脚本 + 与新浪/Yahoo 源的口径对齐标注沿用现有 `source`/`coverage_note` 机制）。

### 2. 交易推送 → 对账与 unknown 窗口

- **增量点**：`wss://webapi-trade.futunn.com/ws` 交易推送（页面侧边栏含概览/登录鉴权/订阅机制/保活/数据格式/错误码完整文档），daemon 常驻订阅订单/成交事件后，「无实时成交推送」缺口补上，对账不再只靠拉取轮询，unknown 窗口可由事件到达时间收敛。
- **前置条件**：常驻 daemon 进程（工作台之外的第二个长活组件）；断线重连后**必须重新登录鉴权并重新订阅**（行情推送配额页明确要求，交易推送大概率同规则，待确认 #3）；事件类型与数据格式子页抓取确认。
- **工作量**：**L**（长连接生命周期管理、重连状态机、事件落库与对账闭环）。

### 3. 增量数据域

- **增量点**：页面侧边栏确认以下域在 REST API 中存在且 MCP 未覆盖或覆盖不全：卖空（每日卖空成交、空头持仓）、股东持股（概况/变动/明细/机构/内部人）、公司行为（分红、**股票回购**、**拆合股**）、资金分布、期权波动率/行权概率。
- **前置条件**：各接口字段、分页与配额逐个确认；落库表结构设计。
- **工作量**：按域逐个 **S**，整体打包 **M–L**；建议先做回购/拆合股（直接服务 K1 复权正确性）与卖空（策略侧增量最直接）。

## 四、风险与边界

1. **A 股实时权限**：平台已实测 A 股仅延时权限（`-9 realtime quote permission required`，见 `TOOL-LIMITS.md`）；行情推送配额页明确行情权限档决定可订阅的市场/品类/深度（LV1/LV2/LV3）。**A 股实时推送预计同样不可用**，A 股继续走日线与延时降级路径；开通后需实测再改路由。
2. **额度挤占**：daemon 批量回填与对话 MCP 若共用同一账号/应用配额，开盘高峰互相挤占。官方只给「错峰、退避」原则不给数值，回填任务必须安排在非交易时段，并给限频器留实测余量；K 线订阅是否吃推送总额度官方自述未定论（待确认 #6）。
3. **与 MCP 通道的职责划分**：**MCP 保留为对话取数**——agent 会话内按需、单标的、拉取式，顺着现有 `futu_mcp.call_tool` 生态；**OpenAPI 作为 daemon 批量/推送通道**——全市场回填、定时任务、常驻 WS 推送。两者都封装进 `trading_datasource`，路由与口径只有一份实现，避免双通道各自维护一套符号/复权逻辑。
4. **凭据安全**：页面明确 OAuth token 不入环境变量、私钥不入库/日志；daemon 凭据管理（加密文件、密钥链、最小 scope）要在设计期落地，不能事后补。
5. **无固定推送配额数值**：任何「订阅 N 个标的没问题」的承诺都不成立，只能按 `code = 4` 超限反馈 + 降级策略（优先可见/核心标的，`quote` 优先于 `order_book`/`ticker`/多周期 `kline`）实现弹性伸缩。

## 五、建议路线

1. **不改变 WP2–WP5 顺序**。OpenAPI 接入是 WP4 之后的**可选升级项**，不插入当前计划。
2. **K1 先行仍用 MCP 方案 A**：现有回填路径（新浪/Yahoo/富途路由 + 口径标注）已可交付，不因本备忘变更。
3. 升级窗口到了再启动，分三阶段：
   - 阶段一：`futu_openapi` REST 只读源——认证（API Key 优先）+ 限频器 + 历史 K 线翻页回填 + 回购/拆合股、卖空两域；
   - 阶段二：行情推送 WS（daemon 常驻，弹性订阅 + 降级）；
   - 阶段三：交易推送接入对账与 unknown 窗口收敛。
4. 每阶段验收都包含**用实测配额数字回填本备忘「待确认」清单**，替换全部假设值。
